# RVO/NRVO 설계 논의 (2026-02-08)

## 배경
- 함수 반환 최적화(RVO/NRVO)를 컴파일러 재량에 둘지, 언어 문법으로 명시할지 논의함.
- 후보는 다음 세 가지였음.
  - 함수 속성으로 `[rvo]`를 붙이고 실패 시 에러
  - 기본은 RVO로 두고, 예외만 `[non-rvo]`로 명시
  - `$ret` 같은 특별 변수를 도입해 작성자가 직접 반환 슬롯 제어

## 핵심 쟁점
- RVO/NRVO가 실제 코드에서 일반적인지
- 기본 정책을 무엇으로 둘지(RVO 기본 vs opt-in)
- 인터페이스/구현 간 컴플라이언스 규칙에 어떤 영향을 주는지
- `return G();`처럼 함수 반환을 다시 반환할 때 최적화 전파 가능성
- `if/else`에서 서로 다른 지역 변수(`a`, `b`) 반환 시 NRVO 가능성

## 논의 요약
1. RVO/NRVO는 현대 컴파일러에서 대체로 흔한 최적화 경로이며, 기본 정책으로 두기 자연스러움.
2. `S F()` 같은 표면 시그니처는 유지하고, 내부 lowering에서 반환 슬롯(sret/out-parameter)로 처리하는 모델이 실용적임.
3. `return G();` 패턴은 타입/경로가 단순하면 반환 슬롯 전달 최적화를 기대할 수 있음.
4. `S a, b; if(cond) return a; else return b;` 형태는 전형적인 단일-객체 NRVO 패턴이 아니므로 보장하기 어려움.
5. C도 본질적으로는 비슷하게 숨은 반환 포인터(sret) 또는 ABI 레지스터 반환으로 복사를 줄임.

## 방향성 결론
- 논의 최종 선호는 `must-rvo` 키워드보다 `[non-rvo]` 중심 모델.
- 권장 정책:
  - 기본: RVO 경로를 요구
  - 예외: `[non-rvo]`를 명시한 함수만 비-RVO 허용
- 즉, “RVO-by-default + explicit escape hatch(non-rvo)” 모델을 채택.

## 인터페이스 컴플라이언스 제안
- `[non-rvo]`를 컴플라이언스에 반영할 경우 규칙 예시:
  - 인터페이스에 `[non-rvo]`가 없으면 구현도 없어야 함
  - 인터페이스에 `[non-rvo]`가 있으면 구현은 있어도/없어도 됨
- 이 방식은 구현이 인터페이스보다 느슨해지는 문제를 방지하고, wrapping으로 성능/의미를 억지 보정하는 상황을 줄임.

## 열린 항목
- `[non-rvo]`의 정확한 의미를 확정할 필요:
  - “복사/이동 허용”인지
  - “RVO 시도 자체 금지”인지
- ABI/IR 단계에서 시그니처와 lowering 계약을 문서화할 필요.
